Rebuild the site after a wipe

Everything in order, for a brand-new server. Written to be read offline with no help. Each command is explained: doas runs a command as root (like sudo), and ~ is your home folder on the server. You can stop after any part; each part works on its own.

Before you start: what must be on YOUR computer

  • The site kit folder (the personal-site repo): htdocs\ and server\install.sh.
  • The riffbox folder (GitHub: Code, Download ZIP; unpack and rename to riffbox; it must hold app, static and deploy).
  • Your latest pulled backup: the copy of the server's /mnt/data/apps/riffbox/backup (it holds db and audio). It is only as new as your last pull. (If the data volume survived, you do not need it: see B3.)
  • In your password manager: the site passphrase, the Riffbox passphrase, and the phone upload token (so the iPhone Shortcut keeps working).
  • Your SSH key (id_ed25519), as the Tech Independence page explains.

A. Tech Independence

Follow the Tech Independence page until your website works. Then upload your htdocs folder as that page says (include htdocs/private/). Do not run ti.sh for your real domain on a second server to "practise": it deletes the domain's DNS records and re-creates them.

B. The site's password rule for /private/

Easy way: one file

Put install.sh (from the kit's server folder) in your home folder on the server, then:

doas sh ~/install.sh --check

doas runs as root; sh runs the file; --check only shows what would change. Nothing is changed.

doas sh ~/install.sh

Applies it. Asks for a user name and a long passphrase (20+ random characters). Safe to run twice.

Undo: doas sh ~/install.sh --remove. Change the password: doas sh ~/install.sh --passwd.

By hand (if the script ever stops working)

doas cp -p /etc/httpd.conf /etc/httpd.conf.pre-kit

Keep a copy of the original so you can put it back.

doas vi /etc/httpd.conf

Open the web server settings. Find the server block that says listen on 127.0.0.1 port 8080. Move to its last line, the } at the left edge. Press O (capital letter o) to open a line above it, then type the three lines below. Press Esc, then type :wq and Enter to save.

  location "/private/*" {
    authenticate "private" with "/htpasswd"
  }

Line 1: any address starting with /private/. Line 2: ask for a password, checked against the file /htpasswd, which is /var/www/htpasswd because the web server is locked inside /var/www. Line 3: end of the rule.

doas htpasswd /var/www/htpasswd YOURUSER

Creates the password file and asks for the passphrase. It is stored only as a bcrypt hash.

doas chown root:www /var/www/htpasswd; doas chmod 640 /var/www/htpasswd

The web server's account (www) must be able to read the file; nobody else may.

doas httpd -n

Checks the settings for mistakes without applying them. It should say configuration OK. If not, put the .pre-kit copy back: doas cp -p /etc/httpd.conf.pre-kit /etc/httpd.conf.

doas rcctl reload httpd

Makes the web server read the new settings. If that errors, use doas rcctl restart httpd.

B2. The site login (one passphrase for every private app and page)

1. Upload the login folder to /home/YOURUSER/login on the server.

doas sh ~/login/deploy/install.sh --check

Look first: it prints what it would create and change, and changes nothing.

doas sh ~/login/deploy/install.sh

Installs the login service, creates /etc/site-auth (a random master key and your passphrase's salted hash; it asks for the passphrase once, 15 characters or more), and asks y before adding /login and /private routes to /etc/relayd.conf (a copy is kept as relayd.conf.pre-sitelogin). It ends with PASS: Site login answers on 127.0.0.1:8099. Then, on your own computer: sh tools/gate-test-login.sh yourdomain (Windows: tools\gate-test-login.ps1 -Domain yourdomain).

Apps installed after this (riffbox, music-share, Version Control) register themselves with the login when their own installer runs. If an app's installer says "the site login is not installed yet", do this section first and re-run it.

B3. The data volume (all apps' data and /pub/)

Every app keeps its data (recordings, databases, backups, restore folders) on the separate plain 100 GB Vultr volume, mounted at /mnt/data. The top level holds only apps/ and _server/; every app is a folder under apps/ (riffbox/, music-share/, version-control/, each with data, backup, restore). /pub/ is the volume's first partition, mounted at /var/www/htdocs/pub. The programs stay on the boot disk and are rebuilt by each app's installer. The full step-by-step, with the one destructive step marked, how to expand it later and the reasons for the layout, is docs/STORAGE.md in the site kit.

After a wiped server the volume still holds your data: do NOT format it again (no disklabel -E, no newfs). In this order:

  1. Before running ti.sh on the new server do mkdir -p /root/my && touch /root/my/storageno (or answer n to its storage question). Without it, ti.sh will try to encrypt or wait for an upload. Do not attach the volume yet.
  2. Finish ti.sh (section A). It recreates the website, mail and calendar (empty).
  3. In Vultr attach the volume (same region as the server), reboot, then doas disklabel sd1 | grep duid. It must equal the DUID in /mnt/data/_server/README (written when the volume was set up; keep a copy in your password manager too).
  4. Add the two lines from that README to /etc/fstab (DUID.a /mnt/data ... and DUID.d /var/www/htdocs/pub ...), then doas mkdir -p /mnt/data && doas mount -a. Check df -h /mnt/data /var/www/htdocs/pub, that /mnt/data/.volume-ok exists (create it with doas touch only if the volume is mounted and the file is missing), that /pub/ lists your files, and doas chown YOURUSER:YOURUSER /var/www/htdocs/pub if needed.
  5. Run each app's installer (sections C and D): it refuses until the volume is mounted; it creates the service user with the uid of the data already on the volume; it never touches the data. No restore step is needed (the in-app restore in section D is only for when the volume itself is lost).

Running ti.sh again later (for example for email) is safe as long as ls /root/my shows storageno and webok. Copy the files listed in docs/STORAGE.md section 0 first and diff them afterwards.

C. Riffbox

1. Upload the riffbox folder to /home/YOURUSER/riffbox on the server. (Only a staging copy: the installer copies it into place.)

ls ~/riffbox/deploy/install.sh

Lists the installer. If it says "No such file", the upload did not arrive or went to the wrong folder.

2. Look first. This changes nothing and says what it would create or change:

doas sh ~/riffbox/deploy/install.sh --check

3. Do it:

doas sh ~/riffbox/deploy/install.sh

On a new server it installs Riffbox's packages (Flask, waitress, ffmpeg), makes the service user and folders, writes the start-up script, and asks: (a) a long passphrase for the Riffbox login (stored only as a salted hash); (b) your existing upload token: paste it from your password manager so the phone Shortcut keeps working, or press Enter for a new one (then put the new one into the Shortcut once); (c) y to add Riffbox's routes to /etc/relayd.conf (a copy is kept as relayd.conf.pre-riffbox). It ends with PASS: Riffbox answers on 127.0.0.1:8100.

Everyday updates later: upload the folder again and run doas sh ~/riffbox/deploy/install.sh --app-files-only (copies only the app and restarts it). If a setting is wrong, --repair shows each fix and asks first.

D. Your recordings (Riffbox data restore)

1. Upload your pulled backup folder (the one holding db and audio) into /mnt/data/apps/riffbox/restore on the server.

2. Open Riffbox in the browser, then Backup and export, then Restoring. It should say it found a backup and how many recordings. Press Restore from this folder. It only works into an empty library, so it cannot overwrite anything, and it never changes the folder you uploaded.

3. If anything is missing or damaged it is listed, not hidden. Waveforms and play copies are rebuilt in the background afterwards.

Practise this before you ever need it, on your own computer: python deploy/practice_restore.py PATH-TO-BACKUP (in the riffbox folder).

E. Check everything (five things)

  1. https://yourdomain/ loads, and https://yourdomain/private/index.html asks for the password (tools\gate-test.ps1 on Windows, tools/gate-test.sh elsewhere).
  2. Log in to Riffbox at /ideas/ and play a recording.
  3. Upload a memo from the iPhone Shortcut (deploy/SHORTCUT.md, section 6, in the riffbox folder).
  4. Press Back up now on the Backup and export page, then confirm a new file appears in /mnt/data/apps/riffbox/backup/db.
  5. Pull /mnt/data/apps/riffbox/backup to your computer again, so the new server has an off-server copy.

F. If something goes wrong

  • Riffbox does not answer: doas rcctl check riffbox then tail -30 /var/log/daemon (the last lines of the server's log).
  • relayd rejects the file: put the copy back with doas cp -p /etc/relayd.conf.pre-riffbox /etc/relayd.conf and doas rcctl reload relayd.
  • FreeFileSync cannot delete or replace files in ~/riffbox: something there is owned by root. Fix once: doas chown -R YOURUSER:YOURUSER ~/riffbox (only that staging folder).
  • Locked out after wrong passphrases: doas rcctl restart riffbox clears the counter.
  • Anything else: every installer has --check; run it and read what it says before changing anything.
